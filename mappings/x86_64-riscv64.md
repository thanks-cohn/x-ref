# x86-64 -> RISC-V RV64 Mapping Guide

This file is not a translation table.

It is a guide for recognizing where an x86 kernel's implementation choices correspond to broader kernel semantics that can be implemented naturally on RV64.

## Rule

Never ask:

> What is the RISC-V instruction equivalent of this x86 instruction?

Ask:

> What kernel property was this x86 mechanism enforcing?

Then map that property to the target architecture.

## Core mappings

| Kernel concern | Common x86-64 mechanisms | Common RV64 mechanisms | X-REF semantic contract |
|---|---|---|---|
| Address-space root | CR3 | SATP | `xref_address_space_activate` |
| Translation invalidation | INVLPG, CR3 reload, INVPCID | SFENCE.VMA | `xref_translation_invalidate` |
| Address-space tags | PCID | ASID | address-space identity/capability |
| Privilege | rings, CPL, descriptors | M/S/U modes | privilege contract |
| Userspace entry | IRETQ/SYSRET paths | SRET | userspace-entry contract |
| Syscall entry | SYSCALL/SYSRET, IDT paths | ECALL/trap | syscall/trap contract |
| Interrupt routing | local APIC / IOAPIC | AIA/PLIC/platform | interrupt contract |
| Inter-processor interrupt | APIC IPI | SBI/AIA/platform IPI | `xref_interrupt_send` |
| Timer | TSC/APIC timer/HPET | `time` CSR, SBI timer/platform timer | timer contract |
| CPU-local storage | GS base / MSRs | `tp`, hart-local storage | cpu-local contract |
| Atomic RMW | LOCK-prefixed instructions | A extension / AMOs / LR-SC | atomic contract |
| Default ordering | relatively strong x86 TSO | RVWMO | explicit ordering contract |
| Port I/O | IN/OUT | normally MMIO | platform I/O contract |
| Page permissions | x86 PTE bits/NX | Sv39/Sv48 PTE bits | mapping/protection contract |
| Hardware virtualization | VMX/SVM | H extension | future virtualization contract |

## High-risk areas

### 1. Memory ordering

This is one of the most important semantic gaps.

Correct x86 code can contain synchronization that works only because x86 provides stronger ordering than the source explicitly requested.

Agents must audit:

- lock-free structures
- publication patterns
- device queues
- page-table publication
- interrupt/shared-state handoff
- scheduler queues
- per-CPU state
- reference counts

Do not fix target failures by scattering arbitrary RISC-V fences until tests pass.

Instead:

1. identify the intended synchronization relation;
2. express it in the common contract or C atomic operation;
3. preserve it on x86;
4. implement the required ordering on RV64;
5. prove with a focused stress/conformance test.

### 2. Interrupt architecture

APIC concepts should not leak into common code.

Common code should express needs such as:

```text
enable external interrupts
acknowledge interrupt source
route interrupt to CPU
send reschedule event to CPU N
mask/unmask source
```

The x86 backend may satisfy these through APIC/IOAPIC. RV64 may involve PLIC, AIA, SBI, or platform-specific mechanisms.

### 3. Boot

Do not force a Multiboot/UEFI/x86 boot shape onto RISC-V.

Normalize boot information into an architecture-neutral structure:

```text
physical memory ranges
reserved ranges
kernel image location
initial CPU identity
firmware/device description
console capability
boot arguments
```

x86 and RISC-V acquire those facts differently.

### 4. Page tables

Do not share raw PTE encodings between architectures.

Common VM code should request mappings with semantics:

```text
READ
WRITE
EXECUTE
USER
GLOBAL
DEVICE
CACHED
```

The backend owns the architecture-specific encoding and legality checks.

### 5. Context switching

The register files differ. The common kernel should care about resumable execution state, not identical register arrays.

Architecture backends may maintain private context structures as long as shared scheduler semantics remain unchanged.

### 6. Userspace transition

A correct port must preserve:

- requested entry point
- userspace stack
- TLS/thread pointer semantics
- argument/register ABI
- privilege reduction
- interrupt/trap state
- address-space activation
- safe return path to the kernel

The exact machine instructions are backend details.

## Discovery patterns

Agents scanning x86 source should search for patterns such as:

```text
cr0 cr2 cr3 cr4
rdmsr wrmsr
invlpg invpcid
cli sti hlt
lgdt lidt ltr
iret iretq syscall sysret
cpuid
xsave xrstor fxsave fxrstor
lock xchg cmpxchg
inb inw inl outb outw outl
apic ioapic
idt gdt tss
__rdtsc
_mm_*
__builtin_ia32_*
```

The result of that scan is an inventory, not a rewrite queue.

Every match must be classified according to the X-REF agent protocol.

## Suggested first migration order

For a conventional x86-64 kernel, a productive RV64 port order is often:

```text
1. portable build boundary
2. boot information normalization
3. physical memory primitives
4. page-table/mapping backend
5. trap/exception entry
6. timer
7. kernel context switching
8. userspace entry/return
9. atomic and ordering audit
10. interrupt controller
11. SMP
12. devices/platform
```

Actual order must still follow the source kernel's first causal boot blocker.

## Non-equivalence ledger

Some source features may have no direct target equivalent or may not be required at all.

Each port should keep a ledger:

```text
source feature
semantic purpose
required by common kernel? yes/no
RV64 strategy
behavioral difference
accepted? yes/no
proof
```

Examples might include particular MSRs, descriptor-table behavior, legacy port I/O, x86-specific debug facilities, or firmware conventions.

The ledger prevents two opposite mistakes:

1. blindly reproducing irrelevant x86 history;
2. silently dropping behavior that the kernel genuinely depends on.

## Goal

The end state should look like this:

```text
                         COMMON KERNEL
                              |
                       X-REF CONTRACTS
                              |
              +---------------+---------------+
              |                               |
          arch/x86_64                     arch/riscv64
              |                               |
      native x86 mechanisms             native RV mechanisms
```

The common kernel should know **what it needs**.

Each backend should know **how its machine provides it**.
